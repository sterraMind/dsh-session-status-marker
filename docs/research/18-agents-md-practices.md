## 2. 长度预算

### 2.1 各来源的建议值

| 来源 | 建议长度 | 关键附加条件 | 来源编号 |
|---|---|---|---|
| GitHub Blog（S2） | 未给行数上限，按「命令、测试、项目结构、代码风格、git 工作流、边界」六个面覆盖 | 超过 2500 个真实仓库的统计；一段真实代码片段胜过三段描述 | S2 |
| AAIF（S3） | 未给行数上限 | 只写智能体无法安全假设的信息；能由格式化器或静态检查强制执行的规则移出文档 | S3 |

| agent-config.com（S6） | 主文件 **约 100 行，最多 120 行** | 它是地图不是疆土，只回答三件事：这是什么仓库、规则是什么、去哪找细节 | S6 |

| chujianyun/skills（S9） | 起始文件 **20–30 行**，`AGENTS.md` 目标 **150 行以内**，300 行以上通常要拆 | — | S9 |
| agents.md 官网（S1） | 无必需字段，纯 Markdown，没有行数要求 | 离被改文件最近的 `AGENTS.md` 优先；显式用户指令覆盖一切 | S1 |

### 2.2 分歧说明

行数建议从 50–120（S8）到 300（S5、S7）不等，跨度很大。S4 给出的解释是：超过 100–150 行后收益反转，原因是继续加内容会诱发智能体过度探索；S6 把同一件事表述为「地图不是疆土」。因此本仓库取 **100–150 行**作为目标区间（与 S4 一致，落在 S8 的上界附近、S6 的上界之外但与其「最多 120 行」的精神一致），并且采用 S4 的渐进披露做法：主文件之外用 `docs/` 下的按需加载文件承接细节。

### 2.3 本仓库现状与差距

现状测量（主会话实跑）：`AGENTS.md` = **128 行 / 28,055 字符 / 约 17.5K tokens**，九个二级标题。

按 §2.1 的建议值对照：

| 维度 | 现状 | 建议区间（S4/S6/S8/S9） | 差距 |
|---|---|---|---|
| 行数 | 128 行 | 100–150 行 | 行数本身达标，但**内容密度不达标** |
| 字符数 | 28,055 | 多数来源以行数衡量；S6 要求「约 100 行、只放五样」 | 单行平均 219 字符，远超「一行一条规则」的密度 |
| tokens | 约 17.5K | — | 每次读取固定消耗约 17.5K 上下文预算 |
| 二级标题 | 9 个 | S6 要求只回答三件事 | 九节里只有两节（命令、边界）是主文件必须回答的 |

行数本身并没有超标，真正的问题是**载荷类型错配**：28,055 字符里绝大部分是编年史、技术栈依据链、逐条失败记录、悬停卡交互细则，这些是 S3 说的「智能体无法安全假设」之外的**可推断或已被别处记录**的信息。S9 明确把「逐文件说明」「易过时的事实」「项目历史」列入应避免清单；S4 把「架构总览过多」和「过多警告」列为两种反模式。

因此重构目标是**改变载荷构成**（S5 明确反对压缩措辞硬塞）：把九节里只有两节原样保留，其余七节按「留在主文件 / 移到 `docs/` / 删除」三种判定重新安置，行数落在 100–150。

| 8 | 安全与审批边界：哪些动作需要人工批准 | S9「需要批准的安全边界」；S2「明确边界（永远不要碰什么）」 |

| 12 | 计划与决策的位置指针 | S6「计划与决策的位置」 |

### 3.2 边界的三档写法

S2 把边界分成三档，这个写法本身比任何单条禁令都有效，本仓库草案照此组织「安全与审批边界」一节：

- **always do**：总是要做（例如事实源以本地镜像的文件:行号为准）。
- **ask first**：先问用户（例如删除文件、发布正式版本）。
- **never do**：永远不做（例如把凭据写进仓库文档）。

S2 还指出最常见的有效约束是「绝不提交密钥」，这与本仓库现行第 9 条一致。

### 3.3 智能体动作句式

S8 要求用「智能体动作」形式写规则：明确命令、明确产物、明确约束（must not / must run / must include evidence），避免无强制力的口号。本仓库草案的每条硬规则都写成「不要 X，要 Y」并给出可执行动作。

### 3.4 优先级顺序

S8 指出硬约束放前面；S1 指出冲突时离被改文件最近的 `AGENTS.md` 优先，显式用户指令覆盖一切；S1 还说明 `AGENTS.md` 是「给编码智能体的 README」，补的是智能体需要的构建步骤、测试、约定，没有必需字段，纯 Markdown。本仓库草案因此把硬规则与命令放在前两节，背景压到一节之内。

## 4. 不该写进主文件的内容与反模式

### 4.1 S9 与 S6 的禁止清单

| 不该写 | 理由 | 来源 |
|---|---|---|
| 长历史与人格设定 | 不影响动作 | S9；S6「不放项目历史、人格设定」 |
| 完整 API 文档 | 智能体不会需要全部 | S9；S6「不放 API 文档」 |
| 模型已知的语言规范 | 智能体本来就会 | S9；S6「不放模型已知的语言规范」 |
| 工具能确定性执行的格式规则 | 应该放进格式化器或静态检查配置 | S9；S6「不放工具已强制的格式规则」；S3「能由格式化器或静态检查强制执行的规则应当移出文档放进工具配置」 |
| 逐文件说明 | 会过时，且与地图重复 | S9；S6「不放逐文件说明」 |
| 空泛建议（写干净代码、用有意义的变量名） | 没有强制力 | S9；S6「不放……易过时的事实」 |
| 易过时的事实 | 版本号、截图路径、上一次发布的字节数 | S9；S6「不放易过时的事实」 |
| 凭据 | 无条件禁止 | S9；S6；S2；S3 |
| 架构文档、API 文档、项目历史 | 主文件是地图不是疆土 | S6 |
| 复制大段既有文档 | 指向即可 | S3（VS Code 的做法是指向既有说明而不是再抄一份） |

### 4.2 vLLM（S5）的加规则六问

加新规则前先问：

1. 智能体本来就会做吗？
2. 只是单次事故吗？
3. 路径会变吗？
4. 是上游文档的复制吗？
5. 和已有规则冲突吗？
6. 别处已经覆盖了吗？

任一命中就不该加。

### 4.3 vLLM（S5）的反模式清单

- **被动堆积**：文档只增不减，越写越长。
- **文件之间复制粘贴**：同一段内容散落在多处，改一处漏一处。
- **命令式高墙**：一长串命令与禁令堆在开头，智能体无法据此做判断。
- **配置快照**：把配置值抄进文档（例：某个版本号、某个字节数），而不是写「怎么拿到这个值」的命令。

本仓库现行 `AGENTS.md` 的第 5 条发布段落正是「配置快照」的反面样本：里面记录了从 1.0.3 到 1.3.0-rc.3 共十四个版本的 tarball 字节数。这些数字已经过时（现行版本是 1.3.1-rc.5），而且拿到字节数的办法是跑 `pnpm pack`，不是查文档。

### 4.4 Augment Code（S4）的两种反模式

- **架构总览过多**：会诱发过度探索（对应本仓库现行「架构红线」一节的证据链与「技术栈」一节的逐项依据）。
- **过多警告**：只写禁令会让智能体过度探索、保守少做，所以每条「不要」都要配一条「要」。

### 4.5 编号的多步工作流

S4 指出「编号的多步工作流」是最强模式之一。本仓库草案的「命令表」用编号步骤表达完成定义，「硬规则」用编号表达配对约束。

### 5.2 判定小结

- 留在主文件：2 节（项目概要、开发回路与可靠命令）。
- 拆开重排：1 节（Standing Orders 拆成硬规则 / 团队分工 / 安全边界）。
- 移到 `docs/`：5 节（架构红线、技术栈、代码风格、已知环境约束、悬停卡交互约束），这五节的正文在仓库里已经存在，本次重构只做指针化，不搬正文。
- 删除正文改为指针：1 节（任务进度看板）。

### 5.3 新增的两个指针
