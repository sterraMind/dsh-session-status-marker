# 13 · 会话状态标记插件对 DSH 的性能影响实测

- 版本：v1（2026-11-20）
- 被测对象：`dsh-session-status-marker@1.2.3`，装在 `$DSH_HOME/profiles/desktop/node_modules/`
- 被测宿主：本机运行中的 DSH Web GUI（Electron 桌面版），Web 端口 57359
- 范围：只做实测与只读分析，未修改任何源码、未重启、未结束任何 DSH 进程
- 采样脚本：`$env:TEMP\.drafts\perf-probe\`（`sample.ps1`、`burst.ps1`、`auth-latency.mjs`、`inspect.mjs`、`ov.mjs`），原始数据在同目录 `out\*.json`

### 1.3 路由耗时与处理器成本

未带凭据直接请求 `/api/*` 一律返回 401（`dsh web authentication required`），因此先解决鉴权再测量。宿主鉴权实现在 `packages/client/connection/src/browser-auth.ts`：cookie 名是 `dsh-auth-<base64url(sha256(authority))>`，值是 `v1.<base64url(JSON{version,authority,issuedAt,expiresAt})>.<base64url(HMAC-SHA256(secret, body))>`，secret 持久化在 `$DSH_HOME\.credentials.yaml` 的 `records['client-connection/browser-session'].payload.secret`。脚本按同一算法在内存中签发 cookie（不落盘、不写 DSH 目录），之后 `api-request-trust.ts:121-151` 的 Host 栅栏对 loopback 放行，请求返回 200。

两组测量：

1. **单次往返耗时**：`node auth-latency.mjs 57359 20`，每条路由顺序发 20 次，取中位数、p90、最大值，同时记录响应字节数；另做 3 路并发各 10 次模拟多标签页。
2. **单次请求的宿主 CPU 成本**：`pwsh -NoProfile -File burst.ps1 -Port 57359 -Count 600`，每条路由先预热 20 次，再连发 600 次，用 57692 进程的 `TotalProcessorTime` 增量除以请求数。这样可以把「网络 + 鉴权 + 路由框架」的固定开销和「插件处理器」的开销分开：插件处理器成本 = 该路由 CPU − 同条件 404 路由 CPU。

## 3. 请求频率模型

设刷新间隔 `I`（`src/contracts.ts:43` `DEFAULT_REFRESH_INTERVAL_MS = 2000`，宿主可在响应里用 `refreshIntervalMs` 覆盖，客户端只接受 ≥250 的值），页面可见的标签页数量 `N_visible`，打开设置页的标签页数量 `N_settings`。

每个页面只有一个模块级定时器（`marks.ts` 的模块单例），与列表里有多少个会话无关；设置页的轮询是另一个独立定时器，只在设置页挂载期间存在。

```
每分钟 list 请求数  R_list     = 60000 / I × N_visible = 30 × N_visible   (I = 2000)
每分钟 overview 请求数 R_overview = 60000 / I × N_settings = 30 × N_settings
每分钟总请求数      R_total    = R_list + R_overview
```

| 情形 | 每分钟 list 请求 | 每分钟 overview 请求 | 合计 |
|---|---|---|---|
| 单标签页可见 | 30（首次多 1 次全量） | 0 | 30 |
| 单标签页可见 + 设置页打开 | 30 | 30 | 60 |
| 3 个标签页可见 | 90 | 0 | 90 |
| 3 个标签页可见，其中 1 个在设置页 | 90 | 30 | 120 |
| 标签页全部隐藏 | 0（定时器仍每分钟空转 30 次，不发请求） | 0 | 0 |
| 标签页从隐藏恢复可见 | 立刻 1 次全量 + 恢复 30/min | 同 | 1 + 30 |

带宽（loopback，不进网卡）：

```
每次条件轮询 = 请求行 11,327 字符 + 响应 8,975 B ≈ 20.3 KB
单标签页每分钟 ≈ 30 × 20.3 KB ≈ 609 KB
```

CPU（用 2.4 的实测单次成本）：

```
单标签页每分钟插件处理器 CPU = 30 × 0.520 ms = 15.6 ms  →  占单核 0.026%
最坏情况（每轮都有变化，走全量）= 30 × 1.230 ms = 36.9 ms  →  占单核 0.062%
3 个标签页可见 = 3 × 15.6 ms = 46.8 ms  →  占单核 0.078%
设置页打开时额外 = 30 × 18.070 ms = 542 ms  →  占单核 0.903%
```

对照 2.1 的实测：w1 窗口内全部 DSH 进程 CPU 合计 61.139 s，折算 56,700 ms/min 量级；单标签页轮询的 15.6 ms/min 占其中约 0.03%。

## 4. 瓶颈判断

### 4.1 插件引入的成本

1. **`overview` 路由是插件侧最大的单项成本**：单次 18.07 ms CPU、14,603 B 响应，是 `list` 全量的 14 倍。原因在 `src/service.ts:317-344`：每次调用都 `ctx.sessions.list()` 建 Map，再对每条标记执行一次 `ctx.sessionTitle.get(session)` 关联标题，75 条记录对应 75 次投影读取，且没有任何缓存。设置页打开期间持续 0.90% 单核，是唯一有实际量级的插件开销。
2. **`revision` 是整份快照文本，不是摘要**：75 条标记对应 8,273 B，随标记数线性增长（约 110 B/条）。它同时出现在条件请求的 URL（11,327 字符）和「未变化」响应的 body 里：该响应 8,975 B，其中 8,273 B 就是 revision，占这个响应的 92%，也相当于全量响应 24,374 B 的 34%。传输走 loopback，因此代价主要是 CPU（序列化 8 KB 字符串）与浏览器侧 URL 构造，不是网络。
3. **条件分支没有短路**：`src/service.ts:299-308` 先 `listAll()` 铺开全部记录、再算完整 `revision`，之后才比较 `since`。所以「没有变化」这条最常见的路径仍然付出全量遍历 + 8 KB 序列化，实测 0.52 ms，是全量 1.23 ms 的 42%。
4. **每个标签页各自轮询**：模块单例的作用域是一个页面，多个标签页之间没有共享，`R_list` 随 `N_visible` 线性增长。实测 3 路并发时单次耗时从 3.89 ms 涨到 8.65 ms，说明宿主单线程串行处理，多标签页会互相排队（但绝对值仍在毫秒级）。

### 4.2 宿主固有的成本（与插件无关）

1. **每个 `/api` 请求 0.65 ms CPU 的固定开销**：404 对照路由实测 0.65 ms，包含 socket 读取、`api-request-trust.ts` 的 Host/Origin 栅栏、`browser-auth.ts` 的 cookie 校验、路由匹配。插件的 `state` 路由（2.46 ms 往返）与 404 基准（2.56 ms）持平，说明轻量路由的成本几乎全在这一层。
2. **宿主主进程的内存增长**：w2 窗口 57692 工作集从 1.84 GB 涨到 1.96 GB（+119 MB），而插件的全部持久数据只有 22 KB，相差三个数量级。增长来源是本会话的流式输出与工具结果，属于宿主固有行为。
3. **renderer 与 gpu 进程的 CPU**：renderer 每分钟 26–27 s、gpu 每分钟 4.8–6.3 s，这是渲染本会话长对话与流式输出的成本。插件在 renderer 侧只做每 2 s 一次 9 KB 的 JSON 解析，未变化时连 React 都不通知（`marks.ts:88`），不构成可观测负载。
4. **ESTABLISHED 7–20 条连接**：宿主自己的 SSE/RPC 长连接，插件不新增长连接——插件的 fetch 复用浏览器的 HTTP keep-alive 连接池，条件轮询间隔 2 s 短于连接空闲回收时间，实测 TIME_WAIT 在两个窗口内都没有增长。

### 4.3 关于「57359 端口 TIME_WAIT」的既有结论

任务描述里提到 `docs/project-memory.md` 第 6 节有「轮询 2s + keep-alive 5s 导致连接重建」的结论。核查结果：

- 在本仓库全部 Markdown（排除 `.research/` 与 `node_modules`）里 grep `TIME_WAIT`、`57359`、`keep-alive`，没有任何命中；`docs/project-memory.md` 的 §6 教训 1–43 中也没有这一条。
- 实测也不支持该描述：轮询间隔 2 s 短于 5 s 的空闲超时，连接会被复用而不是重建；两个 60 秒窗口内 TIME_WAIT 计数分别稳定在 4 和 3。

因此本文不把该结论当作事实引用，只记录本次实测结果。

## 5. 优化候选清单

| # | 改动点 | 预期收益 | 风险 | 是否值得做 |
|---|---|---|---|---|
| A | `revision` 改为固定长度摘要（对现有序列化结果做 sha256 取前 16 字节），Host 与 Client 同时改 | 条件响应 8,975 B → 约 150 B；请求 URL 11,327 字符 → 约 90 字符；单次条件请求 CPU 0.52 ms → 约 0.15 ms；每标签页每分钟省约 600 KB | 中。属于协议变更，需要同时改 `src/contracts.ts` 与 `src/client/marks.ts`；旧客户端发送长 revision 时与摘要不相等，行为退化为每次全量（不会出错）；必须保持「同一份数据在同一份代码下产生同一 revision」这一跨重启性质，对序列化结果取摘要即可满足 | 值得做，但要作为一个版本级变更单独验证 |
| B | 条件响应不再回传 `revision`（客户端已有同值） | 每次未变化轮询省 8,273 B，响应降到约 700 B | 低。`marks.ts:86` 有 `typeof data.revision === 'string'` 守卫，缺字段时保留旧值，下次仍然发 `?since=`，行为不变 | 值得做，改动最小、收益最直接 |
| C | `overview` 按 `list` 的 revision 记忆化标题关联结果，revision 不变时直接返回缓存 | 单次 18.07 ms → 约 1 ms，设置页打开期间 0.90% 单核 → 约 0.05% | 低。缓存键用现有 revision 即可，失效条件与数据变更同源；需要限制缓存条数避免无界增长（只留最近 1 份） | 值得做，是插件侧唯一有量级的 CPU 项 |
| D | 给 `overview` 加 `?since=` 条件请求 | 未变化时省一次渲染 | 低 | 不做。渲染本来就不是瓶颈（`marks.ts` 未变化时不通知订阅者，`StatusOverview` 每次仍会 setState），加条件只增加协议面；C 已经把成本消掉 |
| E | 用 `BroadcastChannel` 让同一浏览器的多个标签页共享一次轮询 | 3 个标签页时从 90 次/分钟降到 30 次/分钟，省约 31 ms/min（0.05% 单核） | 中。需要处理主选举、主页面关闭时的接管、缓存失效广播 | 不做，属于过早优化。典型使用是 1–2 个标签页，省下的绝对值在毫秒级，代价是跨页一致性复杂度 |
| F | 默认 `refreshIntervalMs` 从 2000 提到 5000 | 轮询成本降 60%（省约 9 ms/min） | 低（技术层面） | 不做。用户可见的标记新鲜度从 2 s 退到 5 s，与「标记写入后无需刷新页面即可看到」的设计目标冲突；该值已经是可配置项，需要省电的用户自行调大 |
| G | 给 `list` / `overview` 响应加 gzip | 响应体积降 70% 左右 | 低 | 不做。传输在 loopback，24 KB 的压缩 CPU 高于传输节省，实测宿主侧压缩会引入额外毫秒级开销 |
| H | 把标记存储从 JSON 文件换成 SQLite 或加索引 | 无 | — | 不做。`entries()` 走内存 `Map`（`domain.ts:325`），`list` 路由没有磁盘热点；75 个文件、22 KB 的规模也不构成问题 |
| I | 给自动推断监听器加事件类型前置过滤（在 `inferStatus` 之前判断 `event.type`） | 无 | — | 不做，属于过早优化。`src/service.ts:262` 已经把 `inferStatus` 放在最前面且是纯函数、无 `await`，单次成本远低于一次路由请求；本次也没有测到它进入热点（无计量点，见 1.5） |

优先级建议：B（几行改动、立刻减 92% 的条件响应体）→ C（消掉设置页 0.9% 单核）→ A（协议级变更，随下一个次版本一起做）。E、F、G、H、I 明确不做。

## 6. 结论

1. **插件没有造成卡顿**。单标签页可见时插件的轮询成本是每分钟 30 次条件请求、约 15.6 ms 宿主 CPU、约 609 KB loopback 流量，占单核 0.026%；对照同期宿主全部进程 0.95–1.11 核的占用，占比约 0.03%。未变化时连 React 重绘都不触发。
2. **连接数与句柄没有异常**。两个 60 秒窗口内，57359 上 TIME_WAIT 恒定为 4 和 3，ESTABLISHED 在 7–20 之间随宿主自身长连接波动；宿主主进程句柄 591→592、645→597，renderer 574→574，均无单调增长。插件不建立长连接，只复用浏览器 HTTP 连接池。
3. **内存没有插件相关的异常增长**。w2 窗口宿主主进程 +119 MB、全进程 +125.53 MB，同期插件持久数据只有 22 KB（75 个文件），增长来自正在运行的会话本身。
4. **唯一的真实开销在设置页**：`overview` 路由单次 18.07 ms CPU、没有缓存，设置页打开期间持续占 0.90% 单核。这是插件侧唯一有量级的成本，也是优化清单里优先级最高的两项之一。
5. **一处设计上的浪费**：`revision` 是整份快照文本（75 条标记对应 8,273 B），既放进请求 URL（11,327 字符）又放进「未变化」响应（占该响应的 92%），而且条件分支在比较之前仍然全量遍历与序列化。这一项不影响可用性，但在标记数量增长时线性放大，属于值得改的工程债。
6. **任务描述里引用的 TIME_WAIT 既有结论在本仓库文档中查无出处，本次实测也未能复现连接重建**（2 s 轮询短于 5 s 空闲超时，连接被复用）。后续如果再次遇到连接数异常，应以当时的 `Get-NetTCPConnection` 分布与浏览器连接池状态为证据，不要沿用这条说法。
